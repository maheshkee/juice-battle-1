## 1. What This Product Is

LPG gas cylinder weight monitor for Indian households. An **ESP32-C3 sensor node**
reads a 20 kg load cell via HX711, computes gross weight in grams, and sends
`{grams, quality, sigma}` over WiFi to the **Arduino UNO Q acting as the hub**.
The hub stamps a timestamp, derives cylinder steel via anchor events, computes gas %,
stores in SQLite, runs analytics and prediction, and serves a WebUI dashboard.

**Development phase:** water in a container simulates the cylinder. Weight is weight.
No code path hardcoded for "gas" semantics.

**The fundamental pipeline:**
```
Load cell (YZC-161A 20kg)
    │ 4-wire analog (Red→E+, Black→E-, Green→A+, White→A-)
    ▼
HX711 ADC (24-bit, gain 128, ch A, 10 SPS)
    │ raw counts
    ▼
ESP32-C3 sensor node  [node/]
    │ bit-bang, corrupt filters, N-average, cal_factor → GRAMS
    │ WiFi → { grams: float, quality: GOOD|DEGRADED|FAILED, sigma: float }
    ▼
THE SEAM — hub stamps timestamp on receipt
    ▼
UNO Q hub QRB2210 Linux  [hub/]
    │ steel derivation, gas%, SQLite, analytics, prediction, WebUI
```

**The seam is the most important design boundary.** Node produces grams only.
Hub starts at "receive grams." This never blurs.

## 3. Architecture — Two Contexts, Never Blur

### node/ context (ESP32-C3)

- Flashed via **Arduino IDE or PlatformIO** — NOT App Lab, NOT Bridge
- **Owns:** HX711 bit-bang, corrupt filters, N-averaging, scale-zero tare,
  cal_factor derivation, noise characterisation, WiFi send
- **Outputs grams only.** Never computes gas %. Has no RTC, no history,
  no steel knowledge
- **SAFETY GATE (E-000 chunk 1, non-negotiable):**
  HX711 VCC = 5V. ESP32-C3 GPIO = 3.3V.
  **DOUT/SCK logic levels must be verified before applying power.**
  Level-shift if needed. This is not optional.
- **Pins:** TBD at bring-up. Old DT=D7/SCK=D6 was an STM32U585
  timer-conflict constraint — **VOID on ESP32-C3**. Pick any two GPIO.
- **cal_factor:** Old value of 106.7 raw/g was STM32-specific — **VOID on ESP32**.
  Re-derive from scratch on ESP32.
- **float vs double:** double-broken bug was STM32U585-specific. Re-verify
  on ESP32. Use float as safe default.

### hub/ context (UNO Q QRB2210 Linux)

- App Lab / Docker / Python world
- **Owns:** WiFi receive, timestamp stamping, steel derivation (anchor events
  from SQLite history), gas% = (grams − steel)/14200×100, SQLite, analytics,
  prediction, WebUI
- **Never touches:** raw HX711 counts, pins, bit-bang, cal_factor
- Hub starts at "receive grams via WiFi" — nothing before that
- UNO Q's STM32 MCU is **idle** in V1 — ESP32-C3 owns all sensing

## 4. The Architecture Pivot (Why Everything Changed)

On 2026-06-02, architecture pivoted from:

**OLD (SUPERSEDED/VOID):**
Load cell → HX711 → UNO Q STM32 (DT=D7, SCK=D6, Bridge.notify) → QRB2210 Python

**NEW (current):**
Load cell → HX711 → ESP32-C3 (WiFi) → UNO Q hub (Python, SQLite, WebUI)

**Why:** Separation of sensing from intelligence. ESP32-C3 = dumb sensor,
always on USB power. UNO Q = smart hub. Clean seam via WiFi payload.
Full reasoning in `docs/reference/HANDOFF_ESP32_PIVOT.md` on the board.

**What carries from STM32 era (MCU-agnostic):**
- HX711 bit-bang logic (24-bit + 25th gain pulse, sign extension)
- Three corrupt filters (LONG_MIN, -1, 0x7FFFFF) — always, all three
- N-sample averaging philosophy
- Module result-struct contract {value, quality, diagnosis}
- Self-characterisation (tare, cal_factor, noise — never hardcode)
- Calibration philosophy — everything self-computed per boot from config

**What does NOT carry (STM32-specific, VOID on ESP32):**
- DT=D7, SCK=D6 (timer-conflict, STM32 only)
- cal_factor = 106.7 raw/g (STM32-specific)
- Bridge.notify / Bridge.provide / Bridge.begin() (App Lab only)
- float-only mandate (re-verify on ESP32)
- wait_ready timeout 400ms (tuned for Bridge load, irrelevant on ESP32)
- delay(3000) in setup() (App Lab pattern, not needed on ESP32)

## 5. Key Domain Knowledge — Indian LPG

These facts drive the gas/% math. All PROVEN from official sources.

- Net gas = **14,200g fixed** (BIS standard IS 3196, all domestic cylinders)
- Fill tolerance = ±150g (~1%) — negligible for burn-rate/prediction
- **Steel (empty cylinder weight)** = varies by brand, ~14,500–15,800g
  → must be **measured**, never assumed
- **Capacity** = standardised → can be **classified** from gross weight band
- Full domestic gross ≈ 29.7 kg; commercial 19kg ≈ 35+ kg (well-separated bands)

**The fundamental equation:**
```
gross = steel + gas                    (one equation, two unknowns)
gas%  = (gross − steel) / 14200 × 100
```

**The 52% trap:** `gross/full × 100` gives ~52% on an EMPTY cylinder.
Always use `(gross − steel) / 14200`.

**How steel is learned (no user input needed):**
- **Full install anchor (primary):** `steel = gross_at_install − 14200`
  Fires on every refill, guaranteed. Accuracy ±150g (~1%).
- **Empty floor (opportunistic cross-check only):** `gross ≈ steel` when
  gas ≈ 0. Not depended upon — users swap before empty.

**Error budget:**
- Fill tolerance ±150g: negligible (constant offset, cancels in burn-rate)
- cal_factor drift ~6.5% ≈ 923g on full cylinder: **the real enemy**
- Engineering attention goes on cal_factor stability, not fill tolerance

**Δ-tracking is calibration-free:**
`Δ = gross_earlier − gross_later` cancels steel completely.
Consumption, burn rate, patterns work from day one.
Only absolute gas% and days-remaining need steel.

## 8. V1 Scope (Locked)

From `docs/SCOPE.md` on the board.

**In V1:**
- V1 assumption: every cylinder placed is a fresh full delivery (14.2 kg gas)
- Three states: UNINSTALLED → TRACKING → LOW GAS
- Outputs: gas_kg, gas_pct, days_remaining, burn_rate, last_updated, state
- burn_rate and days show "—" until 24h of data exists
- No government averages — all numbers from this household's actual readings

**Explicitly excluded from V1:**
- Partial cylinder at first install (stays UNINSTALLED until G-jump)
- Brand selection or user input for tare
- Commercial cylinder sizes (5kg, 19kg)
- Multi-cell load cell (single cell only)
- Fleet / multi-cylinder

**Key thresholds (all derived, not arbitrary):**
- REFILL_THRESHOLD_KG = 6.0 (min G-jump when cylinder replaced)
- CYLINDER_REMOVED_KG = 2.0 (below this = cylinder absent)
- LOW_GAS_KG = 2.0 (alert threshold)
- LOW_GAS_DAYS = 10 (time-based alert)
- HEARTBEAT_MIN = 15 (SQLite snapshot cadence)
- MIN_HOURS_BURNRATE = 24 (min data before computing burn rate)

## 9. What Tomorrow's Session Designs — E-000

**Goal:** ESP32-C3 + HX711 first clean raw read. Gate for everything else.

**E-000 has three chunks in sequence:**

**Chunk 1 — 3.3V logic-level verification (safety gate, before powering):**
HX711 DOUT outputs at VCC logic level. If HX711 VCC = 5V, DOUT swings to
~5V. ESP32-C3 GPIO is 3.3V. Overvoltage on ESP32 GPIO = potential damage
or corruption. Must characterise this BEFORE connecting.

Questions to answer in chat:
- What is the actual DOUT high-level when HX711 VCC = 5V?
- What is the ESP32-C3 GPIO maximum input voltage?
- Is a level shifter needed, or does the HX711 DOUT naturally swing lower?
- If level-shift needed: which method (resistor divider vs dedicated IC)?

**Chunk 2 — Pin selection:**
Any two GPIO on ESP32-C3. No timer-conflict constraints (that was STM32).
Questions to answer: which GPIO are safe (not strapping pins, not flash pins)?
Strapping pins to avoid: GPIO2, GPIO8, GPIO9. Flash-connected to avoid
on variants with in-package flash: GPIO12–17.

**Chunk 3 — First raw read:**
Minimal bit-bang sketch. No cal, no tare. Just: read raw 24-bit count,
apply three corrupt filters, print raw value to serial.
Gate: stable, non-corrupt raw stream.
